# CRM API

Backend для интеграции **Dentist Plus + Bitrix24** с последующим переходом на **WhatsApp-автоматизацию**.

---

## О проекте

Этот проект — backend-обвязка для стоматологической клиники, где:

- **Dentist Plus** используется как основная медицинская система
- **Bitrix24** используется как CRM для воронок, сделок и контроля обращений
- **backend** управляет логикой обработки обращений, записью, переносами, отменами, напоминаниями и синхронизацией
- в дальнейшем сюда подключается **WhatsApp-бот** и FaaS-автоматизации

Текущая логика строится по схеме:

**WhatsApp / backend → Dentist Plus → Bitrix24**

## Что уже реализовано

На текущем этапе проект уже умеет:

### Dentist Plus
- авторизоваться в Dentist Plus
- получать филиалы
- получать врачей
- искать пациента по номеру телефона
- создавать пациента
- получать расписание врача
- получать визиты врача
- учитывать пагинацию визитов
- рассчитывать свободные слоты по расписанию и занятым визитам
- создавать визит
- изменять визит
- отменять визит
- получать визит по `visitId`

### Bitrix24
- создавать или обновлять контакт
- создавать или обновлять основную сделку в воронке **«Заявки и обращения»**
- создавать отдельную визитную сделку в воронке **«Визиты»**
- двигать стадии сделок
- оставлять комментарии в сделках
- хранить связь с Dentist Plus через `patientId` и `visitId`

### Flow / бизнес-логика
- обрабатывать входящее сообщение
- искать или создавать пациента
- синхронизировать пациента с Bitrix24
- создавать визит и переводить основную сделку в статус **«Записан»**
- отменять визит
- переносить визит
- отмечать **неявку пациента**
- формировать **напоминание о визите**
- синхронизировать изменения по **уже известным визитам**
- не импортировать вручную созданные визиты из Dentist Plus
- не спамить одинаковыми sync-комментариями, если изменений нет

## Текущая архитектура

### Dentist Plus хранит:
- пациентов
- врачей
- филиалы
- расписание
- визиты

### Backend отвечает за:
- обработку входящих обращений
- поиск или создание пациента
- расчет свободных слотов
- запись пациента на прием
- перенос / отмену / no-show
- формирование напоминаний
- синхронизацию изменений в Bitrix
- бизнес-логику воронок
- будущую интеграцию с WhatsApp

### Bitrix24 отвечает за:
- CRM-взаимодействие
- воронки
- стадии сделок
- контроль обращений
- визуализацию записи и ее статуса для администраторов

---

## Важное архитектурное правило

### Bitrix24 хранит только наши визиты

В Bitrix попадают **только те визиты, которые были созданы через наш backend / WhatsApp-цепочку**.

Это значит:

- если визит создан через наш API — он считается **нашим**
- если визит создан вручную в Dentist Plus — он **не импортируется** в Bitrix
- если наш визит потом вручную изменили или удалили в Dentist Plus — его можно синхронизировать обратно в Bitrix
- если визита в Bitrix нет — `sync-known-visit` **ничего не создает**

Это защищает CRM от хаоса и мусора.

## Bitrix24

Используется входящий webhook.

### Воронки сделок

- `categoryId = 0` → **Заявки и обращения**
- `categoryId = 1` → **Задачи и звонки**
- `categoryId = 3` → **Визиты**

### Стадии основной воронки (`categoryId=0`)

- `NEW` → Новый лид
- `PREPARATION` → Думает
- `PREPAYMENT_INVOICE` → Не дозвонились / не ответили
- `EXECUTING` → Записан
- `FINAL_INVOICE` → Не пришли

> Стадиями вроде **«Не дозвонились / не ответили»** сейчас управляет администратор вручную.

### Стадии воронки визитов (`categoryId=3`)

- `C3:NEW`
- `C3:PREPARATION`
- `C3:PREPAYMENT_INVOICE`
- `C3:WON`
- `C3:LOSE`

---

## Кастомные поля Bitrix

### Контакты

- `UF_CRM_1773483540591` → Dentist Plus ID
- `UF_CRM_1773483553643` → Нормализованный телефон

### Сделки

- `UF_CRM_1773483593452` → Dentist Plus Patient ID
- `UF_CRM_1773483603764` → Dentist Plus Visit ID
- `UF_CRM_1773483785404` → Источник канала

### Enum источника канала

- `45` → WhatsApp
- `47` → Звонок
- `49` → Сайт
- `51` → Instagram
- `53` → Другое

# Flow endpoints

---

## 1. Входящее сообщение

### `POST /api/flow/incoming-message`

Что делает:
- ищет пациента по номеру
- если не найден — создает пациента
- создает/обновляет контакт в Bitrix
- создает/обновляет основную сделку

Пример body:

```json
{
  "phone": "+77789478095",
  "message": "Здравствуйте, хочу записаться"
}
```

---

## 2. Создание визита

### `POST /api/flow/visit-created`

Что делает:
- создает визит в Dentist Plus
- создает визитную сделку в Bitrix
- переводит основную сделку в **«Записан»**

Пример body:

```json
{
  "patientId": 5368060,
  "doctorId": 1333453,
  "branchId": 5061,
  "start": "2026-03-16 13:00:00",
  "end": "2026-03-16 13:30:00",
  "description": "TEST API"
}
```

---

## 3. Пришел на визит

### `POST /api/flow/patient-arrived`

Пример body:

```json
{
  "patientId": 5368060,
  "visitId": 14540079
}
```

---

## 4. Не пришел на визит

### `POST /api/flow/patient-no-show`

Что делает:
- переводит основную сделку в **«Не пришли»**
- переводит визитную сделку в **LOSE**
- пишет комментарии

Пример body:

```json
{
  "patientId": 5368060,
  "visitId": 14540079
}
```

---

## 5. Отмена визита

### `POST /api/flow/visit-cancelled`

Что делает:
- отменяет визит в Dentist Plus
- переводит основную сделку в **«Думает»**
- переводит визитную сделку в **LOSE**
- пишет комментарии

Пример body:

```json
{
  "patientId": 5368060,
  "visitId": 14540079,
  "reason": "Пациент отменил запись"
}
```

---

## 6. Перенос визита

### `POST /api/flow/visit-rescheduled`

Что делает:
- переносит визит в Dentist Plus
- подтягивает новые данные в Bitrix
- оставляет основную сделку в **«Записан»**

Пример body:

```json
{
  "patientId": 5368060,
  "visitId": 14540079,
  "doctorId": 1333453,
  "branchId": 5061,
  "start": "2026-03-17 15:00:00",
  "end": "2026-03-17 15:30:00",
  "description": "Перенос теста",
  "reason": "Перенос по просьбе пациента"
}
```

---

## 7. Напоминание о визите

### `POST /api/flow/send-visit-reminder`

Что делает:
- получает актуальный визит
- формирует текст напоминания
- пишет комментарий в Bitrix

> Пока сообщение реально не отправляется, только формируется.

Пример body:

```json
{
  "patientId": 5368060,
  "visitId": 14540079,
  "phone": "+77789478095"
}
```

---

## 8. Синхронизация известного визита

### `POST /api/flow/sync-known-visit`

Что делает:
- синхронизирует **только уже существующий визит из Bitrix**
- если визит найден в Dentist Plus — подтягивает актуальные данные
- если визит удален/отменен вручную в Dentist Plus — трактует это как отмену
- если визита нет в Bitrix — ничего не создает
- не спамит одинаковыми комментариями, если изменений нет

Пример body:

```json
{
  "visitId": 14540079,
  "patientId": 5368060
}
```

# Текущая бизнес-логика

## Воронка: Заявки и обращения

- Новый
- Не дозвонились
- Думает
- Записан
- Не пришел

## Воронка: Визиты

- Новый
- В работе / промежуточные стадии
- Lose — отмена / no-show / сорванный визит

> Некоторые стадии администратор может двигать вручную, это нормально.

# Что важно знать

На текущем этапе проект **не строится вокруг Dentist Plus leads API** как основной CRM-логики, потому что практическая работа с lead API оказалась ограниченной.

Поэтому сейчас проект сфокусирован на самой надежной части:

- пациент
- расписание
- врачи
- визиты
- слоты
- запись
- синхронизация с Bitrix
- flow обработки обращения
